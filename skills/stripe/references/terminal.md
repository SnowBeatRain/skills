# Stripe Terminal

Use this reference for in-person payments with Stripe Terminal, reader connection, connection tokens, Tap to Pay, and card-present PaymentIntents.

## Architecture

A Terminal integration typically includes:

- server creates Connection Tokens
- app or POS connects to a reader
- server creates a PaymentIntent for in-person collection
- reader collects payment method
- server and webhooks reconcile final status

Connection Tokens are short-lived and should be generated by the server for an authenticated operator or location.

## Payment Method Types

Terminal is the main exception to the general rule against hardcoding `payment_method_types`. In-person card-present flows require `card_present`; Canada may require `interac_present` where supported.

## Locations and Readers

Model physical locations and reader assignment. Do not let a reader from one store or connected account process payments for another without explicit authorization and auditability.

## Connect and Terminal

For platforms, confirm which account owns the reader, location, PaymentIntent, charges, disputes, and payouts. Connect + Terminal requires careful account context and operational support for reader onboarding.

## Offline and Network Failure

If using offline-capable flows, define risk limits, reconciliation behavior, and operator guidance. Offline acceptance can change fraud and settlement risk.

## Testing and Operations

- Test reader discovery, connection, collection, cancellation, and retry.
- Verify receipts, refunds, and disputes.
- Monitor reader connectivity and failed collections.
- Keep support procedures for lost, reassigned, or replaced readers.

## Common Mistakes

- Reusing connection tokens too broadly.
- Treating reader collection as final before server/webhook reconciliation.
- Ignoring location ownership and operator authorization.
- Mixing online Checkout assumptions with card-present behavior.
